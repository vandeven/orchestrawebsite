# Logging and audit trail

[← Back to plan](PLAN.md)

## Goal
Make it possible to see what the website is doing and what went wrong, and to trace every change that admins and the master make. Normal logs help to find and fix errors and attacks. A separate audit trail records who changed what and when, so a mistake or misuse by an admin account can be traced (for rights changes: who changed whose rights). Logs are written to Cloud Logging, which is built into Google Cloud and free at this size (see [hosting](hosting.md)).

**Access level:** this feature has no pages on the website. Logs are read in the Google Cloud console by the owner of the Google Cloud project.

## User stories
- As the site owner, I want to see errors and attacks in one place, so I can fix problems quickly.
- As the site owner, I want to see who made an edit and when, and for rights changes who edited whose rights, so I can find out how a mistake happened and undo it by hand.
- As the site owner, I want to be told when something goes wrong, without watching the logs.
- As a member, I want the website not to keep more personal data in its logs than needed.

## Functional requirements

### Application logs
1. LGG-1: The application writes structured JSON log lines to standard output (with the Quarkus JSON logging extension). Cloud Run sends them to Cloud Logging automatically. There are no log files, no log agent and no third-party logging service.
2. LGG-2: Every log line has a timestamp, severity (DEBUG, INFO, WARNING, ERROR), message, the name of the component that wrote it, a request ID, the version of the application (see HOS-35), and the ID of the logged-in user when there is one.
3. LGG-3: Every request gets a request ID, generated by the server. A request ID sent by the browser is not trusted. The ID is in every log line of that request and in a response header, so one request can be followed through the logs and a user can report it.
4. LGG-4: These events are logged:
    - application errors, with the stack trace in the log only (never in the response, see [security scanning](security-scanning.md), SEC-20)
    - security events: failed and locked logins, password changes ([my account](my-account.md)), rate limit hits, refused access (403), missing or invalid CSRF tokens, invalid recovery tokens
    - failures of outside services: Firestore, Cloud Storage and the email service
    - start of the application (with the result of the configuration check, never the values), and the result of the master account setup job
5. LGG-5: These are **never** logged: passwords, `PASSWORD_PEPPER`, `MASTER_PASSWORD`, API keys, session tokens, recovery tokens, CSRF tokens, signed URLs, the contents of contact form messages, and the full text of editable pages. Email addresses of visitors who are not logged in are not logged either; where an identifier is needed (for example a failed login), a hash of it is logged. IP addresses are only logged as a hash.
6. LGG-6: The log level is INFO in production. DEBUG is off in production. The level is set with the environment variable `LOG_LEVEL`, which only accepts DEBUG, INFO, WARNING or ERROR.
7. LGG-7: Health check requests are left out of the logs, so they do not use up the free quota or hide real events.
8. LGG-8: All logs, including the audit trail, are kept for 30 days (decided). This is the default of Cloud Logging and it is free. Cloud Run's own request logs contain visitor IP addresses, which is personal data under GDPR, so the period is not extended.

### Audit trail of admin actions
9. LGG-9: **Every action by an admin or the master that changes something is logged as an audit entry**, whether it succeeds, is refused or fails:
    - [user management](user-management.md): add a user, send a recovery email again, remove a user, make a member admin, take away admin rights
    - [member page](member-page.md) and song management: add, edit (title and notes), archive, unarchive and permanently delete a song, add, rename and remove a file
    - [content editor](content-editor.md): save or clear an editable text, upload and delete an image
    - login and logout of admins and the master, and the master account setup job (HOS-19)
10. LGG-10: Every audit entry contains:
    - the time and the request ID
    - who did it (the actor): user ID, email address and role of the admin or master
    - what: a fixed action name (for example `user.remove`, `song.delete`, `text.save`, `image.delete`)
    - on what (the target): the type and ID of the target, with a readable name (for example the email address of the removed user, the title of the song, the key of the text, the file name)
    - the result: `success`, `denied` (not allowed) or `failed` (error)
    - the useful details of the change: for a role change the old and new role; for a file the type, name and size; for a text only its key (the content of the text is not logged, decided)
11. LGG-11: **Rights changes always log both people:** when someone's rights are edited (make admin, take away admin rights) or a user is added or removed, the entry contains the actor (who made the change) and the target (whose rights or account changed), each with user ID and email address, and for a rights change the old and the new role. Attempts that are refused are logged as well, for example a member who sends a request to an admin endpoint, or an admin who tries to remove another admin (USR-11). The audit entry is written once per action and does not depend on the response that the user sees.
12. LGG-12: The audit trail cannot be switched off in the application, and an action is not completed without its audit entry being written to the log output.
13. LGG-13: Audit entries are marked with a fixed field (`audit=true`), so the owner can filter them in Cloud Logging. They are kept for 30 days like all other logs (LGG-8). There is no separate log bucket and no extra cost.
14. LGG-14: The audit trail is protected from the people it describes:
    - The Cloud Run service account only has permission to write logs (`roles/logging.logWriter`), not to read, change or delete them.
    - Admins and the master of the website cannot read or change logs from the website. Only the owner of the Google Cloud project can read them, in the Logs Explorer.
    - The log settings (retention, filters, alerts) can only be changed by the project owner.
15. LGG-15: The documentation of the project lists ready-made log queries for the owner, for example: everything one user did, every change to one text, every deleted song or user, every refused admin request, and all admin logins.

### Alerts and cost
16. LGG-16: Log-based alerts in Cloud Monitoring send an email to the owner when:
    - there is a burst of errors (for example more than 10 in 5 minutes)
    - there is a burst of failed or locked logins
    - the master account setup job fails
    - the daily cap on contact messages is reached
    - the master account logs in (see [security hardening](security-hardening.md), HRD-9)
    - an audit entry shows a refused admin action from a member account (someone who should not be there)
17. LGG-17: Logging stays within the free allowance: no DEBUG in production, no health checks, and no large payloads in log lines (a log line is at most 8 KB). The monthly budget alert (HOS-9) also covers Cloud Logging.

### Safety of the logs
18. LGG-18: Everything that comes from a user (for example a song title, a file name, a text key or an email address in a failed login) is written as a value in the JSON structure, never inserted in a message as raw text. Control characters and line breaks are removed and values are cut at 200 characters, so nobody can add fake log lines (log injection).
19. LGG-19: The privacy page of the website (see [legal pages](legal-pages.md)) says that logs and the admin audit trail exist, which data they contain and how long they are kept (30 days).

## Content and data
- **Application log line:** timestamp, severity, message, component, request ID, user ID (optional), extra fields per event.
- **Audit entry:** the fields in LGG-10 plus `audit=true`.
- **Google Cloud settings:** the log-based alerts, the saved log queries and the permission of the Cloud Run service account. The retention is the default 30 days.
- **Environment variable:** `LOG_LEVEL`.

## Input validation
This feature has no pages or forms. These inputs are checked:
- **`LOG_LEVEL`:** optional, one of DEBUG, INFO, WARNING or ERROR (not case sensitive). In production, DEBUG is refused and the application starts with INFO and logs a warning.
- **Request ID:** generated by the server. A request ID header from the browser is ignored (LGG-3).
- **Values in log lines:** all user-provided values are cleaned before they are logged: control characters and line breaks removed, at most 200 characters, written as JSON values (LGG-18).
- **Audit action names:** only from a fixed list. An unknown action name is a programming error and fails the tests.

## Automatic tests
The tests capture the log output of the application, so no real Cloud Logging is needed.
- **Format (LGG-1, LGG-2, LGG-3):** every log line is valid JSON with the required fields; all lines of one request have the same request ID; a request ID header sent by the browser is not used.
- **Events (LGG-4):** a failed login, a lockout, a refused request (403), an invalid CSRF token, an invalid recovery token and an error in an outside service each produce a log line with the right severity, and the response to the user contains no stack trace.
- **Audit entries (LGG-9, LGG-10, LGG-11):** a table-driven test performs every admin action in LGG-9 as an admin and as the master, and checks that exactly one audit entry is written with the right action name, user, target, result and details. The same actions are tried as a member and as an anonymous visitor, and each gives a `denied` entry (or a security event for anonymous requests) and no change.
- **Refused and failed actions (LGG-11):** an admin who tries to remove another admin (USR-11) and an action that fails because of a storage error both give an audit entry with the right result.
- **Rights changes (LGG-11):** making a member admin, taking away admin rights, adding a user and removing a user each log the actor and the target with ID and email, and for rights changes the old and the new role.
- **Text changes (LGG-10):** saving a text writes only the key and the actor, and the text itself is not in the log.
- **No secrets in logs (LGG-5):** a test runs the full login, password recovery, set password, contact form, upload and download flows with fake secrets, and then searches all captured log output for the passwords, the pepper, tokens, signed URLs, the contact message text and visitor email addresses; none may appear. IP addresses only appear as a hash.
- **Log injection (LGG-18):** values with line breaks, quotes, braces and control characters (for example in a song title or a file name) end up as one JSON value, in one line, cut at 200 characters.
- **Log level (LGG-6, LGG-7):** an invalid `LOG_LEVEL` is refused; DEBUG is not accepted in production; health check requests are not logged.
- **Cannot be switched off (LGG-12):** a test that removes the audit logger configuration fails the application start or the test.
- **Infrastructure checks (LGG-14, LGG-16):** the infrastructure policy checks (see [infrastructure](infrastructure.md), INF-8) checks the alerts and that the service account only has the log writer role.
- **Privacy page (LGG-19):** the privacy page mentions the logs, the audit trail and the 30 day retention.

## Additional requirements
- **No costs:** only Cloud Logging and Cloud Monitoring, within their free allowances, with the default 30 day retention.
- Logs follow the GDPR requirements in the [plan](PLAN.md#privacy-and-security): minimal personal data and a limited retention.
- Logging must not slow down requests or cold starts: it only writes to standard output.

## Out of scope
- A page on the website to read or search the logs. The owner uses the Google Cloud console.
- Keeping earlier versions of texts or files (see [content editor](content-editor.md)), and logging the content of texts. The audit trail shows that and by whom something changed, not the old content.
- Keeping the audit trail longer than 30 days.
- Logging every page view or building statistics (analytics).
- Sending logs to a third-party logging service.
